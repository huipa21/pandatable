## Scope

- Implement D-020 auto-indexing for qualifying fields used by shared-view sort, group, filter, or quick search when the physical table has more than 10,000 rows.
- Create indexes asynchronously with `CREATE INDEX CONCURRENTLY`; use btree for supported sort/group/filter use and trigram GIN for supported quick-search use, consistent with the existing query and field-type capabilities.
- Track successful automatic index creation in `meta.fields.options.indexed`, keeping metadata truthful through retries, failures, and repeated scheduling.
- Add focused coverage for eligibility, index selection, idempotency, metadata updates, and failure/retry behavior.
- Validate the linked AT-512 performance target against 200k rows. AT-512 is also listed for T2.15: report benchmark evidence distinctly from auto-index job correctness, and do not claim the performance criterion passes without measuring it.

**Out of scope:** a manual index-management UI/API, indexing personal-view usage, schema migrations that rewrite applied migrations, and unrelated query or performance tuning.

## Contracts to respect

- D-020 is binding: FK and unique-field indexes remain as specified; auto-indexes are only for eligible fields in shared views on tables strictly larger than 10k rows. No manual index UI in v1.
- Never run `CREATE INDEX CONCURRENTLY` inside a transaction. Use validated/quoted identifiers and follow existing database error conventions; do not mark metadata indexed before the database confirms success.
- Reuse existing worker/lifecycle patterns. Keep index creation safe under duplicate triggers and process restarts; surface failures and allow a later retry.
- Preserve existing query behavior and permissions. Do not treat transient search or personal-view configuration as a shared-view indexing trigger.
- Keep field option JSON compatible and preserve unrelated option values when updating `indexed`.
- Any new non-trivial technical choice requires a D-xxx entry; do not silently change D-020.
