## Scope

- Add the admin Ownerships view for a disabled user, showing their directly owned workspaces and allowing all ownerships to be transferred to a chosen active user.
- Complete orphaned-workspace rescue in Admin → Workspaces: assign an active user as owner and verify that user receives normal owner access.
- Add an explicit hard-delete flow requiring the admin to type the target username. Delete the user's solely owned workspaces and their physical schemas, personal views, and attachments in deleted scopes. Preserve shared workspace data, replacing remaining authorship references with “Deleted user”.
- Pass AT-113, AT-114, and AT-115 with API, database, and real-browser coverage as appropriate.

Out of scope: user self-service deletion, deletion of shared workspaces, changing disable/re-enable semantics, implicit admin access to workspace data, and unrelated user/group administration.

## Contracts to respect

- Disabling remains a soft operation: it retains data and authorship. Hard delete is a separate, irreversible, admin-only operation.
- A workspace is orphaned when it has no active direct user owner. Rescue must grant workspace ownership to the chosen active user and preserve the direct-active-owner invariant (D-023); group-only ownership is not sufficient.
- Transfer ownerships covers every direct workspace ownership of the disabled user. Do not expose workspace data to admins or weaken normal ACL checks.
- Hard delete removes workspaces only where the target is the sole owner; remove associated physical objects and files consistently. Do not delete shared workspaces or their data. Preserve remaining records and display deleted-user authorship.
- Make multi-resource changes atomic where required; handle sessions, grants, ACL cache invalidation, foreign keys, and filesystem cleanup consistently with existing lifecycle and trash/purge patterns. Surface partial/failed cleanup explicitly; never report destructive success when work remains.
- Enforce administrator authorization server-side. Validate the typed username against the target user and localize all new visible strings and errors in both `en` and `zh-CN`.
- Reuse existing admin user/workspace UI, API, database, and confirmation patterns. Add a new `D-xxx` decision for any non-trivial behavior not settled by D-021, D-023, FR-U5/FR-U6, or the acceptance criteria.
