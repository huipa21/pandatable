## Scope

- Implement client-side undo/redo per tab with a maximum of 50 successful actions, covering cell edits, paste/fill-down, row inserts/deletes, link/unlink, and view configuration changes. Group each user action coherently and keep redo history correct when a new action follows an undo.
- Add the authorized `rows:restore` operation needed to restore deleted-row snapshots with the same IDs, row values, links, and attachment references. Deleted-row comments must remain associated with the restored IDs.
- Detect when a cell targeted by undo changed after the original edit; require explicit confirmation before overwriting the other user's value.
- Pass AT-608 and AT-609.

Out of scope: undoing schema changes (use Trash), durable or cross-tab history, and unrelated changes to row/link/view behavior.

## Contracts to respect

- D-033: stack is in-memory per browser tab, bounded to the last 50 actions; restored row identity must be preserved (`BY DEFAULT`).
- Follow the inverse-operation table and conflict rule in `docs/10-collaboration.md` §5. Capture prior values/snapshots from authoritative mutation responses or a valid local snapshot; do not create undo entries for failed/no-op mutations.
- Restore only through normal authorization and validation boundaries. Preserve row IDs and attachment/link references; use existing transaction and error conventions. Do not silently report success for partial restoration.
- Schema changes are not undoable. Localize all new visible strings in both `en` and `zh-CN`; keep keyboard actions usable and accessible.
