## Scope

- Implement transactional history capture for existing row writes and link/unlink mutations, plus one table-level `type_change` event for field conversion; satisfy AT-607.
- Add the paged, read-authorized row-history API and the localized History timeline in the row expand modal.
- Add the daily retention job using `history_retention_days` (default 90); cover the cutoff and deletion behavior with tests.

Out of scope: undo/redo and row restore (T3.5), a tamper-proof audit log, and changes to unrelated mutation or authorization behavior.

## Contracts to respect

- Use the existing `meta.row_history` schema; capture history in the same transaction as the mutation, using PostgreSQL 18 `RETURNING OLD/NEW` as appropriate.
- `changes` is keyed by field ID and records changed values only; inserts contain `n`, deletes contain the full `o` snapshot. Exclude system and virtual fields.
- Bulk changes create one history record per affected row. Link/unlink records are written for both rows and include the other row's ID and display value. Row deletion does not erase history; table purge cascades it.
- A field conversion produces one `type_change` record with a NULL `row_id`, not one per converted row. D-071 governs the distinction between row and table events.
- Enforce effective table read access on history reads. Preserve existing mutation transaction and realtime notification behavior (D-183); do not add a separate event channel.
- The timeline is grouped by user and minute. Localize every visible string in both `en` and `zh-CN`; do not resolve row authorship UUIDs through the sharing directory.
- This is row history, not an audit log. Reuse existing API pagination, error, and UI patterns; record a new decision if a required behavior is not already specified.
