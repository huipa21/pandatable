## Scope

- Run the complete M0–M3 acceptance suite, including the milestone-end production-image E2E. Track each criterion against its existing evidence; update only affected acceptance evidence and reopen any affected tasks when the full run fails.
- Write a concise end-user guide at `docs/user-guide.md` in English and Simplified Chinese. Cover only verified, shipped workflows; keep the two language versions equivalent and do not claim unsupported behavior.
- After the release gate passes, commit the release changes, create the `v1.0.0` tag, then build/save and deploy that version to the configured, authorized target server. Verify app health and the public HTTPS/Caddy route after deployment.
- Update `progress.md` with one T3.12 row and one newest-first change-log line. Do not claim the release is complete unless deployment checks pass.

## Out of scope

- New product features, changing acceptance thresholds, or treating prior partial/manual evidence as passing without performing the required check.
- Changing server secrets/configuration or Caddy/network setup without explicit server-owner authorization. Do not expose secrets in logs, command output, docs, or commits.
- Pushing the tag or publishing release artifacts unless the configured release process explicitly authorizes it.

## Contracts to respect

- D-158 and `docs/14-dev-build-release.md` §4: `ptdev check` must pass, then run the complete production-image `ptdev e2e` once at this milestone end and before tagging. A failure reopens affected tasks; do not substitute `--fast` for this phase gate.
- Acceptance status must reflect observed results. Record unavailable infrastructure, unperformed manual checks, and any remaining blockers as partial/blocked; do not create the tag unless the complete acceptance gate passes. If deployment fails after tagging, report the tagged release as not deployed; do not claim completion.
- Follow `docs/13-deployment.md` for the target host, image transfer, upgrades, backups, and health checks. Deploy only to the explicitly configured/authorized host; if none is available, stop before deployment and tagging and report the blocker.
- The guide must accurately reflect the shipped UI and use matching English and Chinese sections. Do not add frontend strings or dependencies.
- No new decision is expected. If a necessary non-trivial release choice arises, add a new `D-xxx` entry without rewriting decision history.

## Verification (D-158)

1. Before long runs, follow the environment preflight in `AGENTS.md`; write full gate output to a log and inspect failures.
2. Run `go run .\tools\ptdev check`.
3. Run `go run .\tools\ptdev e2e` once for the complete production-image phase gate. Do not rerun it to diagnose environment problems; resolve the environment first.
4. Once checks pass and release changes are committed, create `v1.0.0` as specified by the release procedure; build/save that tag and deploy it using the documented procedure. Verify server-side health and the real HTTPS/Caddy route (including WebSocket behavior where available). Do not report internal health alone as successful external reachability.
5. Check the guide's bilingual coverage and links, inspect acceptance/progress diffs, and verify the tag points to the intended release commit. Report deployment failure as a blocker even if the tag already exists.
