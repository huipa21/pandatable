## Scope

- Build a streamed ZIP containing `db.dump`, attachment files under `files/`, and `backup.json`; record successful backups in `meta.backups`.
- Implement the documented `pandatable restore <archive> --yes` CLI flow: validate archive/metadata and compatible versions, replace database objects and files, then run migrations. Keep restore CLI-only; UI restore is out of scope.
- Pass AT-706, AT-707, and AT-708. AT-707 is manual acceptance on a fresh host; add focused automated restore coverage and record the manual limitation honestly.

Out of scope: point-in-time recovery, incremental backups, UI restore, remote backup storage, and unrelated dashboard or deployment work.

## Contracts to respect

- Use `pg_dump --format=custom --no-owner` with the configured database URL; the application image must provide `pg_dump` 18. ZIP deflate output is streamed to `$PT_DATA_DIR/backups/pandatable-YYYYMMDD-HHMMSS.zip`; `backup.json` contains `{appVersion, schemaMigration, createdAt, pgVersion, fileCount}`.
- Preserve a consistent database snapshot. Attachments are copied after the dump, so newer files may be present; orphan cleanup is handled by the existing purge job.
- Permit only one backup job at a time; run it at low priority (`nice`; `ionice` is not available in the container). Before starting, refuse when free disk is below 2 × (database size + files size), with an explicit localized error.
- Enforce admin authorization for create/list/download/delete. Surface job failures; do not record failed or partial backups as successful. Keep file and `meta.backups` lifecycle consistent.
- Restore is destructive: require the documented confirmation flag, validate the ZIP and versions before replacing data, use the documented `pg_restore --clean --if-exists` sequence, replace `files/`, and run migrations. Never silently report success after a failed restore step.
- Localize all new visible strings in both `en` and `zh-CN`; follow existing API error, job, download, and filesystem patterns.
