## Scope

- Implement view creation, rename, duplicate, delete, and reorder in the
  production grid, keeping shared views distinct from user-owned personal
  views. Duplicates retain the source's supported configuration.
- Enforce the permissions matrix: readers may manage their own personal views;
  shared-view changes require write/owner; only owners may lock/unlock shared
  views. A user's personal view is not visible to other users.
- Locked/shared views remain usable with unsaved in-memory overrides. Offer
  “save as personal view” without writing those changes to the shared view.
- Preserve optimistic concurrency for every persisted edit. Verify AT-506
  (including reader-created personal vs shared views), AT-507, and AT-508.

## Contracts to respect

- Extend the existing `PATCH /views/{id}` behavior rather than regressing
  T1.21: require the authoritative view version, return a version conflict for
  stale writes, and increment the view version once per committed mutation.
  Keep the table schema version unchanged.
- Read `docs/06-permissions.md` §4 and D-148 carefully: T1.21 deliberately
  limits persisted column edits to write/owner on unlocked views. T2.10
  implements the broader view-management matrix; do not retain that limitation
  where it contradicts AT-506/507, or bypass ownership/lock checks.
- Merge and sanitize supported config members without dropping existing
  members such as row height, filter, sort, group, highlight, or aggregates.
  Keep temporary overrides local until explicitly saved as a personal view.
- Keep personal views private to their owner (404 to other users); shared views
  are only shared with users who already have table access. Do not add public
  sharing or other out-of-scope integrations.
- Use existing API error, authorization, version-conflict, and frontend stale
  request patterns. Localize every new visible string in both `en` and
  `zh-CN`; keep view controls keyboard/touch accessible.
- Add focused backend, frontend, and production-browser tests for lifecycle,
  permissions, lock/override behavior, ordering, and a two-client conflict
  that reloads and reapplies the second edit. Record any new non-trivial
  technical choice as a D-xxx entry.
