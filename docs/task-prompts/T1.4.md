## Scope

- Implement `acl.Resolver` for effective permissions. App role (`admin|user`)
  and resource grants are independent. Effective access is the maximum of the
  user's and flat groups' applicable grants along workspace → book → table;
  lower grants never restrict inherited access (D-011, D-013). Disabled users
  have no access. Admin has no implicit workspace data access.
- Implement the documented per-request path/group lookup and bounded
  per-process cache/invalidation approach in `docs/06-permissions.md`. Follow
  D-045 single-instance constraints. Define cache epochs/invalidation so any
  grant or group-membership mutation cannot leave stale authorization. Add a
  decision if implementation requires a meaningful change to the documented
  approach.
- Add middleware/helpers for requiring `read`, `write` or `owner`, including
  404 for resources hidden from the caller. Do not add workspace/table/nav/data
  services planned for later tasks.
- Implement only the T1.4 grant API: list direct grants/inherited summary,
  `PUT /api/v1/grants` upsert and `DELETE /api/v1/grants/{id}`. Enforce the
  scope-owner rule: an effective owner of S may manage grants on S and its
  descendants, including owner grants, but may not manage outside S (D-014).
- Validate polymorphic resource and principal references in the service. Reject
  missing/trashed targets, invalid target/principal types, missing or disabled
  user principals, missing group principals, and malformed levels with typed
  safe errors. Serialize mutations where needed to preserve D-070 validation

- Enforce the last-owner invariant on changes that remove/downgrade a direct

### Delivered

- `internal/acl`: `Level` (none<read<write<owner), `Resource`, strict UUID
  parsing, `Access{Level, Visible}` with `Check(required)` (404 hidden / 403
  visible-but-low). `Resolver` runs **one SQL statement per lookup** (groups
  joined in SQL; live W→B→T path; disabled users and trashed
  targets/ancestors → none; path-only visibility via live descendants) behind a
  per-process LRU (4096 entries, 5 s TTL) with an epoch: `Invalidate()` clears
  everything and a lookup that began before the bump is never stored.
- `acl.Service` grants API logic: `List` (owner-only, repeatable-read snapshot:
  direct grants with principal info + `inheritedLevel`, ancestor summary),
  `Put` (upsert; same-level no-op), `Delete`. Mutations: cheap uncached owner
  pre-check, then one transaction taking `FOR NO KEY UPDATE` on the workspace,
  `FOR KEY SHARE` on book/table, `FOR SHARE` on the user/group principal (each
  a separate statement, fixed order), re-checking ownership uncached under the
  locks, validating the principal (404/409), enforcing last-owner (active direct
  user owners only), and invalidating the cache after any write.
- `internal/httpapi/acl.go`: `GET/PUT /api/v1/grants`, `DELETE /api/v1/grants/{id}`,
  `authHTTP.authenticated` and the reusable `authHTTP.require(level, type,
  param)` guard + `UserFromContext`. Routes mount only when `AuthOptions.ACL` is
  set; `cmd/pandatable/serve.go` wires `acl.NewResolver`/`NewService`.
- sqlc: second `sqlc.yaml` entry → `internal/acl/aclsql` (pinned 1.31.1,
  regeneration byte-identical).
- Docs: 05 (hard-delete lock protocol), 06 (visibility/implementation), 09
  (T1.4 contract), 14 (test commands), decisions D-079/D-080, progress, this
  record, acceptance-tests evidence, and the [T1.5 prompt](T1.5.md).

### Ambiguities resolved (see D-079/D-080)

Only effective owners may list grants; "hidden" = no effective grant and no
live descendant grant, so a book owner gets 403 on the parent workspace and
404 on a sibling book; same-level PUT is an unchanged no-op (201 create / 200
replace); disabled user principals are 409, missing 404; a disabled owner's
grant may be removed (the workspace is already orphaned); disable/trash/
membership services must call `Invalidate()` (the 5 s TTL is only an
out-of-band bound).
