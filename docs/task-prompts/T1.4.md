## Scope

- Implement `acl.Resolver` for effective permissions. App role (`admin|user`)
  and resource grants are independent. Effective access is the maximum of the
  user's and flat groups' applicable grants along workspace → book → table;
  lower grants never restrict inherited access (D-011, D-013). Disabled users
  have no access. Admin has no implicit workspace data access.
- Implement the documented per-request path/group lookup and bounded
  per-process cache/invalidation approach in `docs/06-permissions.md`. Follow
  D-045 single-instance constraints. Define cache epochs/invalidation so any
  grant or group-membership mutation cannot leave stale authorization. Add a
  decision if implementation requires a meaningful change to the documented
  approach.
- Add middleware/helpers for requiring `read`, `write` or `owner`, including
  404 for resources hidden from the caller. Do not add workspace/table/nav/data
  services planned for later tasks.
- Implement only the T1.4 grant API: list direct grants/inherited summary,
  `PUT /api/v1/grants` upsert and `DELETE /api/v1/grants/{id}`. Enforce the
  scope-owner rule: an effective owner of S may manage grants on S and its
  descendants, including owner grants, but may not manage outside S (D-014).
- Validate polymorphic resource and principal references in the service. Reject
  missing/trashed targets, invalid target/principal types, missing or disabled
  user principals, missing group principals, and malformed levels with typed
  safe errors. Serialize mutations where needed to preserve D-070 validation
  against future hard deletion; do not add polymorphic FKs or triggers.
- Enforce the last-owner invariant on changes that remove/downgrade a direct
  active-user owner grant on a workspace. At least one active **direct user**
  owner must remain; group-only ownership does not count. Disabling a user may
  orphan a workspace per D-014, but no disable service belongs in T1.4.
- Keep `read < write < owner` raise-only semantics. A lower direct grant must
  not reduce inherited access. Admin role alone grants no resource access.
- Unsafe mutations reuse exact configured Origin + `X-PT-CSRF: 1`, request
  limits, no-store, timeout and typed-error handling. Enforce `must_change_password`
  and disabled-user rules on protected API paths.
- No migrations unless a demonstrated schema defect requires a new forward
  migration. Never edit applied migrations or modify schema integrity decisions
  D-069..D-071. No admin user/group CRUD UI, user lifecycle, workspace/data APIs,
  frontend grants UI, SSO, API tokens, public sharing or unrelated work.
